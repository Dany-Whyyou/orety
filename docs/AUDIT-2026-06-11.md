# Audit du projet Orety — 11 juin 2026

**Verdict global : base solide et bien structurée, mais 3 failles d'isolation multi-tenant dans les policies RLS et 23 erreurs TypeScript à corriger avant toute mise en production.** Point clé : le web contourne les RLS (service role) avec des contrôles applicatifs incohérents, tandis que les apps mobiles s'appuient à 100 % sur des RLS qui ont des trous cross-organisation.

---

## 🔴 Critique — à corriger avant toute donnée réelle

### 1. Fuites cross-organisation dans les policies RLS

- **Profs / affectations lisibles entre organisations** : les tables `profs`, `prof_matieres` et `affectations` n'ont pas de colonne `organisation_id`, et leurs policies (`supabase/migrations/20260420180012_rls_policies.sql`, lignes ~419-462) se contentent de `has_permission('profs.lire')` sans filtre d'organisation. Un admin d'une école A pourrait lire les profs et affectations d'une école B.
- **Coefficients modifiables hors scope** : `coefficients_write` (lignes ~401-410) utilise `has_permission('structure_scolaire.gerer')` sans `can_access_etab()`, contrairement à `niveaux_write` qui le fait correctement. Asymétrie SELECT (filtré) / WRITE (non filtré).
- **Incidents** (`supabase/migrations/20260421120000_incidents.sql`, lignes 91-99) : la policy `incidents_staff_write` référence une permission `eleves.modifier` qui **n'existe pas dans le seed** (clause morte), et ne vérifie ni l'organisation ni l'établissement alors que la table a ces colonnes.

Tant qu'il n'y a qu'une seule organisation (Orety), c'est invisible — mais bloquant pour l'ambition SaaS multi-tenant.

### 2. Le web utilise exclusivement la service role key, avec des contrôles de rôle incohérents

Toutes les queries et actions passent par `createAdminClient()` (`web/src/lib/supabase/admin.ts`) qui contourne les RLS. La défense repose uniquement sur les checks applicatifs, or :

- `web/src/app/admin/layout.tsx` vérifie seulement l'authentification, **pas le rôle** — tout utilisateur connecté (y compris parent ou prof) peut afficher toutes les pages admin et leurs données.
- Les `requireAdmin()` des actions sont incohérents : `secretariat` accepté dans `actions/eleves.ts` et `actions/parents.ts`, mais refusé dans `actions/profs.ts`, `actions/classes.ts` et `actions/matieres.ts`. À harmoniser et centraliser.
- Le `etablissement_scope_id` de l'utilisateur n'est jamais utilisé pour filtrer les requêtes.

### 3. 23 erreurs TypeScript — le build est probablement cassé

`tsc --noEmit` échoue avec 23 erreurs sur 10 fichiers. Trois familles :

- **Resolvers zod/react-hook-form** : les schémas avec `z.coerce` (string → number) créent un mismatch input/output dans `affectation-dialog.tsx:88`, `classe-dialog.tsx:70`, `evaluation-dialog.tsx:108`, `incident-dialog.tsx:99`.
- **Enum `sexe` désynchronisé** : le code envoie `"f" | "m" | "autre"` alors que le type généré attend `"M" | "F"` (`actions/eleves.ts:119`) — possible bug d'insertion réel. Même problème sur le statut d'inscription dans `actions/cloture.ts:53` et `:82`.
- Types Recharts/queries dans `queries/rapports.ts` (5 erreurs) et `queries/dashboard.ts` (3 erreurs), plus `rapports-view.tsx:231` et `actions/incidents.ts`.

## 🟠 Important

- **Mots de passe générés affichés en clair** (`actions/profs.ts`, `actions/parents.ts`) : pas de TTL, pas de log d'audit, et le rôle est dupliqué dans `user_metadata` (risque de désynchronisation avec `utilisateurs.role_id`, la vraie source de vérité). Préférer un système d'invitation / premier-login-force-reset.
- **FK parent fragile** : `eleves.cle_parentale` référence `utilisateurs.pseudo` avec `ON UPDATE CASCADE` (`20260420180006_eleves.sql`). Changement de pseudo parent risqué ; envisager pseudo immuable ou FK sur l'UUID.
- **Aucune pagination** : `getEleves()` et consorts chargent tout ; `.limit(1000)` / `.limit(5000)` arbitraires dans dashboard et rapports.
- **Erreurs avalées dans les queries** : en cas d'erreur Supabase, les queries loggent et retournent `[]` — l'utilisateur voit « Aucun élève » au lieu d'une erreur.
- **Mobile : duplication intégrale entre les deux apps** : `auth.dart` (159 lignes), `theme.dart` (151 lignes) et `splash_screen.dart` copiés-collés entre `mobile/prof` et `mobile/parent`. Créer un package partagé `packages/orety_core/`.
- **Aucun test** nulle part (web et mobile).

---

## 🟡 Mineur

- ~19 dialogs web répètent le même pattern (useForm + reset + submit + toast) — un `<FormDialog>` générique diviserait le code par 5 ; schémas zod dupliqués entre dialogs et actions.
- Mobile : dépendances jamais utilisées (`flutter_dotenv`, `fl_chart`, `intl`) ; tous les boutons métier sont des stubs `onPressed: () {}` (apps = prototypes d'auth fonctionnels, zéro feature métier).
- Pas de soft delete sur les données académiques (notes, bulletins supprimés = irrécupérables).
- Index manquant sur `seances(date)`.

---

## ✅ Points forts constatés

- Schéma SQL bien conçu : 45+ index, FK toutes indexées, cascades réfléchies (`restrict` sur niveaux/matières), triggers `updated_at`, enums typés, recherche trigram.
- Toutes les fonctions `SECURITY DEFINER` fixent correctement `search_path`.
- Pattern SSR Supabase correct côté web (middleware + cookies via `@supabase/ssr`), `server-only` sur les queries, zod partout, `strict: true`.
- Seeds propres (aucune donnée sensible), `.env.local` bien gitignoré.
- Clé anon hardcodée dans les apps mobiles : pratique standard Supabase, acceptable **à condition que les RLS soient étanches** — d'où l'urgence du critique n° 1.

---

## Plan d'action recommandé

1. **RLS** : ajouter le filtre organisation/établissement aux policies `profs`, `affectations`, `coefficients_write`, `incidents_staff_write` ; corriger la permission orpheline `eleves.modifier`.
2. **Web** : ajouter un check de rôle dans `admin/layout.tsx`, centraliser `requireAdmin()` avec une matrice de rôles unique.
3. **TypeScript** : corriger les 23 erreurs (en commençant par l'enum `sexe` et le statut de clôture, vrais bugs potentiels d'insertion).
4. Ensuite : invitations à la place des mots de passe en clair, pagination, package Flutter partagé, premiers tests.
